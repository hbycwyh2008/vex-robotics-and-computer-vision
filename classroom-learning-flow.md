# Classroom Learning Flow — VEX Robotics

This course uses the same shared classroom learning culture as the Full-Stack Web and AI course:

> **Learn → Practice → Rebuild → Share**

The shared flow keeps expectations consistent across CS and engineering courses. In VEX Robotics, that flow is expressed through an engineering-specific cycle.

## Shared Course Flow

### 1. Learn
Observe a phenomenon, review prior evidence, learn one new concept, or study a short teacher demonstration.

### 2. Practice
Build, program, configure, measure, or test the new pattern with support.

### 3. Rebuild
Reproduce the important pattern with less support. Rebuilding may mean rebuilding a mechanism, reconfiguring devices, rewriting control logic, repeating a test procedure, or recreating a vision pipeline.

### 4. Share
Explain the result, document evidence, compare approaches, defend a decision, and identify the next engineering step.

# VEX Engineering Cycle

Within the shared course flow, VEX lessons repeatedly use:

> **Predict → Build / Program → Test → Debug → Redesign → Retest → Document → Explain / Transfer**

## Predict
State what you expect the system to do and why.

## Build / Program
Create or modify the physical mechanism, wiring, configuration, code, sensor logic, or computer-vision system.

## Test
Use a defined procedure. Whenever the claim involves reliability, accuracy, or improvement, use repeated trials rather than one successful run.

## Debug
Use evidence to identify what is actually failing.

Recommended debugging pattern:

> **Symptom → Hypothesis → Test → Evidence → Decision**

## Redesign
Change one or more justified parts of the system: hardware, control logic, parameters, mechanism geometry, sensor placement, or test conditions.

## Retest
Repeat the relevant test so the team can compare before and after results.

## Document
Record the engineering evidence in the **Team Engineering Notebook** and complete the **Individual Engineering Learning Log**.

## Explain / Transfer
Explain why the system behaved as it did and apply the same engineering idea to a new challenge or constraint.

# Standard Evidence Rule

A working robot is not enough by itself.

Before a major task is considered complete, students should be able to answer:

1. What were we trying to accomplish?
2. What did we build or change?
3. How did we test it?
4. What evidence did we collect?
5. What failed or behaved unexpectedly?
6. What did the evidence cause us to change?
7. What happened after the change?
8. What can I personally explain or rebuild now?

> **Build / Program → Test → Record → Explain**

If a result is not documented, it cannot be used as engineering evidence.

# Team Evidence and Individual Evidence

## Team Engineering Notebook

The team records the shared engineering process:

- goals and constraints;
- sketches and design decisions;
- robot/code/vision configuration;
- test procedures;
- measurements and observations;
- failures and debugging;
- changes and redesigns;
- retest results;
- next steps;
- evidence links.

## Individual Engineering Learning Log

Each student records personal learning and contribution:

- what I worked on;
- what engineering decision I understand;
- what problem the team encountered;
- how it was diagnosed;
- what I personally contributed;
- what I can now explain or rebuild without help.

The team notebook shows **what the team engineered**. The individual log shows **what each student learned and contributed**.

# Connection to Mastery Levels

The course uses `mastery-levels.md`:

- **Level 0:** Exposure
- **Level 1:** Follow and make it work
- **Level 2:** Explain while looking
- **Level 3:** Rebuild with a checklist
- **Level 4:** Rebuild independently
- **Level 5:** Modify, debug, and transfer

The engineering notebook should make growth through these levels visible over time.
