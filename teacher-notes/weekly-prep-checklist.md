# Weekly Teacher Preparation Checklist

Use this once per week. The goal is to prevent avoidable class loss from batteries, missing parts, stale code, unclear deliverables or untested demos.

## 1. Curriculum
- [ ] Read this week's two core meeting plans.
- [ ] Open the matching anchor lesson(s).
- [ ] Write the launch prompt where students can see it on entry.
- [ ] Identify the one concept/demo that must stay under ~15 minutes.
- [ ] Confirm the evidence students must submit each meeting.
- [ ] Prepare exit checks; do not improvise them after cleanup starts.

## 2. Hardware
- [ ] Batteries charged and labeled.
- [ ] Brains/controllers power on.
- [ ] Required sensors/motors/cables available.
- [ ] Tools complete enough for every active team.
- [ ] Spare fasteners/shafts/collars available.
- [ ] Field/test area marked and clear.
- [ ] Known broken hardware separated and labeled.

## 3. Software
- [ ] VEXcode opens on student machines.
- [ ] One teacher robot/device can connect and download.
- [ ] Starter code opens without missing configuration.
- [ ] Required Python packages/OpenCV environment verified for CV weeks.
- [ ] Sample images/video files open locally.
- [ ] Coursera videos assigned/accessible before the meeting if required.

## 4. Demonstration
- [ ] Run the demo yourself once before class.
- [ ] Know the expected observation.
- [ ] Prepare one intentional failure or comparison when useful.
- [ ] Decide what students must predict before you show the result.
- [ ] Do not prepare a full project solution for students to copy.

## 5. Student Materials
- [ ] Daily engineering lab sheet available.
- [ ] Project delivery pack section shared when a project begins.
- [ ] Team notebook accessible.
- [ ] Individual learning log accessible when scheduled.
- [ ] Test sheet/data table ready before physical testing starts.

## 6. Assessment
- [ ] Practical checkpoint materials ready if scheduled.
- [ ] Teacher answer key open if using quiz-bank questions.
- [ ] Rubric/checklist visible before project validation.
- [ ] Reassessment target is a specific skill, not “redo everything.”

## 7. Failure Continuity
For the week's main hardware/software risk, decide the fallback task before class.

- [ ] configuration/code review
- [ ] notebook/evidence work
- [ ] offline sensor/vision data analysis
- [ ] debugging checklist
- [ ] test-plan design
- [ ] rebuild/parts practical
- [ ] portfolio/code review

## 8. End-of-Week Reset
- [ ] batteries charging/stored safely
- [ ] broken parts tagged
- [ ] team kits restored
- [ ] final code committed
- [ ] missing evidence noted
- [ ] reassessment list created
- [ ] next week's consumables/parts identified

## Five-Minute Readiness Test
Before the first meeting of the week, you should be able to answer:

1. What do students do in the first 10 minutes?
2. What are they building/programming/testing by minute 25?
3. What measurement or evidence will exist by minute 75?
4. What individual understanding will I check at the end?
5. What happens if the robot or software does not work?
